# ADR 0005: 人数増加と将来運用に備え、鍵なし認証を標準とする

- Status: Proposed（レビュー/マージでAccepted）
- Date: 2026-11-14
- Supersedes: ADR 0004 の認証JSONキー運用を許容した部分（非公開Sheets自体の決定は維持）

## 背景
開発者は現在2名（Windows / macOS）。今後増員・デモから本番へ拡張する可能性がある。サービスアカウント秘密鍵JSONを複数人へ配布すると、漏洩時の被害や失効/ローテーション負荷が増える。

## 決定
1. 人間のローカル開発は、個別のGoogleアカウントでGoogle Cloud CLIにログインした上で、専用**読み取り専用SAのなりすましADC**を使う。各人に**SA単位**のToken Creator権限を付与する。
2. SAは非公開Googleシートの閲覧者とし、プロジェクトOwner等は付けない。人間のシート編集権限は別に管理する。
3. サービスアカウントJSON**秘密鍵を作らず、使わない**。コードは長期秘密鍵型のADCを拒否する。ログやCIに認証情報を含めない。
4. Google Cloud実行リソースでは**関連付けたSA**を使用。GitHub Actions等のOIDC環境に実アクセスが必要となったら**WIF + SA**を設計する。今のCIはモックのみ。
5. 認証・デプロイ・課金・実データアクセスは人間の承認ゲート。Windows/macOSの個別操作手順を管理する。

## 理由と結果
- 長期鍵を配布せず各人単位のアクセス取り消し・監査が可能。
- Google Sheets API呼び出し/データ契約/分析ロジックは変更不要（ADCは実行環境に応じた資格情報を自動取得）。
- IAM Service Account Credentials APIとGoogle Cloud CLIの設定が必要で、チームへの初回設定説明が増える。
- キーレスでも**ローカルADCファイルのユーザー認証情報が残る**ため、PC管理と退職者の権限剥奪を省略できない。
- 料金・権限リスクはゼロではなく、利用量確認と人間の承認を継続する。

## 比較した選択肢
- JSON秘密鍵をメンバーへ配布：簡単だが漏洩リスクとローテーション負荷が高く不採用。
- 個人のOAuthユーザーADCで直接シートにアクセス：追加OAuthスコープなど構成が環境依存になりやすく、アプリとしての実行主体の一貫性も弱い。
- 常時WIFをローカル端末へ導入：Googleが推奨するWIFは外部IdP/OIDCワークロード用であり、現時点の人間のPC2台には過剰。
- 選定：ローカルなりすまし、将来のCloud実行SA、必要時WIF。
